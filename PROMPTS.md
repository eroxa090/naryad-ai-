# Промпты для Claude Code: каждому участнику свой

Порядок старта:
1. Человек 1 запускает свой промпт ПЕРВЫМ. Через ~1 час он пушит в `main` каркас: package.json, структуру папок, `shared/types.ts`, миграции.
2. Человек 2 и Человек 3 сразу клонируют репозиторий и начинают в своих папках. Где нужно, используют заглушки, пока каркас не в `main`, потом подтягивают `main`.
3. Все открывают ИИ-агента в корне репозитория. Общий контракт лежит в `AGENTS.md`: Codex читает его автоматически, Claude Code тоже (через `CLAUDE.md`, который его импортирует). Промпты подходят для обоих агентов без изменений.

## Человек 3: ИИ-модули и аналитика

```
Ты работаешь в репозитории НарядAI. Сначала полностью прочитай AGENTS.md: это общий контракт команды.
Я Человек 3, моя зона: api/ai/** и analytics/**. Чужие папки НЕ трогай. Типы бери из shared/types.ts.
Можно импортировать api/_lib (supabase admin, проверка JWT, notify) от Человека 1. Если его ещё нет в main, сделай временный api/ai/_lib/ и потом переключись.
Работаю в ветке `ai`. БЮДЖЕТ НА ИИ ВСЕГО $8: следи за этим жёстко.

Правила экономии (обязательно):
- Переменная AI_MOCK=true: все эндпоинты возвращают правдоподобную заглушку той же формы, без вызова API.
- Модели из env: AI_MODEL_FAST (Haiku 4.5) для parse-order, assistant, suggest-worker; AI_MODEL_SMART для check-order, shift-report, insights
  (в разработке тоже Haiku, на демо переключим на claude-sonnet-5-5).
- Используй официальный @anthropic-ai/sdk, structured outputs / tool use с strict JSON-схемами, prompt caching для системного промпта со справочниками.
- Фото отправляй сжатыми ≤1000px. Логируй usage (input/output tokens) каждого вызова в консоль.
- Перед отправкой в LLM заменяй ФИО на ID (функция maskPII).

ПЕРВЫМ ДЕЛОМ (за 1 час): закоммить и сделай PR со ВСЕМИ эндпоинтами из AGENTS.md в режиме AI_MOCK, чтобы фронт мог интегрироваться.
Потом по порядку делай реальную логику:
1. /api/ai/transcribe: Groq whisper-large-v3, русский и казахский.
2. /api/ai/parse-order: текст мастера → JSON карточки. Справочники участков, оборудования и шифров (с нормативами) в кэшируемом системном промпте.
   Нечёткое совпадение названий оборудования («насос два на обогащении» → Н-2), поле confidence.
3. /api/ai/suggest-worker: скоринг на SQL/TS БЕЗ LLM (свободен, нужная специальность, лучший рейтинг по этому типу оборудования,
   меньше очередь) + короткое объяснение reason шаблоном.
4. /api/ai/check-order (главный модуль). Сначала детерминированные проверки (бесплатно):
   полнота (работы, шифр, материалы, фото «после» для аварийных), время против норматива и срока, материалы против typical_qty (перерасход),
   АНТИФРОД фото: taken_at не раньше начала работ, perceptual hash через sharp, сравнение со всеми прошлыми фото этого оборудования.
   Затем ОДИН вызов LLM: соответствие работ проблеме, логичность материалов и шифра, сравнение фото до/после (мультимодально),
   оценка 1–5 и photo_score, explanation для мастера, worker_feedback для исполнителя. Если уверенность низкая, needs_master_review=true.
   Итоговый verdict, запись в ai_reviews; при needs_rework → RPC change_order_status(action='rework') и notify исполнителю с причиной.
5. /api/ai/shift-report: статистика SQL-запросами + LLM пишет короткую текстовую сводку.
6. /api/ai/assistant: вопросы мастера («кто свободен из электриков?», «что просрочено?», «отчёт за неделю по обогащению»).
   Tool use с инструментами-запросами к БД, отвечать коротко.
7. analytics/run.py (pandas, scikit-learn, supabase-py; requirements.txt): по истории нарядов найти
   топ проблемного оборудования и участков, повторные отказы одного шифра, поломки вскоре после ППР, связь со сменой, исполнителем и бригадой,
   аномальный расход материалов (IsolationForest), рост внеплановых нарядов → риск отказа 0..1 по каждой единице оборудования.
   Все ЧЕТЫРЕ закономерности из AGENTS.md должны находиться. Цифры считает Python. LLM вызывается один раз на весь запуск
   и превращает найденное в выводы с рекомендациями («Конвейер К-3: 7 внеплановых остановок за 30 дней, 5 из них — М-02. Рекомендуем…»).
   Результат пишется в ai_insights (включая kind='equipment_risk' с data.risk для карты здоровья).
8. Подготовь для презентации 3–4 примера: реальный вход и выход check-order (хороший наряд; наряд без фото и с лишними материалами; старое фото).
```
